## UI Areas and State

`App` in `src/App.tsx` renders the toolbar and desktop three-pane workspace. The desktop grid contains the folder sidebar, note list, and editor, separated by two accessible resize handles. At viewport widths up to 760px, a separate mobile rendering shows one pane at a time using the `mobileStage` state (`folders`, `notes`, or `editor`) and Back actions.

React `useState` owns folders, notes, selection, query, view mode, sidebar visibility, pane widths, mobile stage, and menu visibility. `useMemo` derives folder notes, search results, and recency/pinned groups. Selection and preferences are not persisted.

## Data Model

The current serializable model is defined in `src/data/store.ts`:

- `Folder`: `id`, `name`, `color`, `createdAt`.
- `Note`: `id`, `folderId`, `title`, `body`, `createdAt`, `updatedAt`, `pinned`.
- `AppState`: arrays of folders and notes.

`Note.body` is editor HTML. There is no explicit attachment, editor-document, user, or preference type. IDs are generated by `createId` from a prefix, timestamp, and random suffix.

## Data Flow and Operations

1. `App` calls `loadAppState()` once to initialize its folder and note state.
2. `loadAppState()` reads `nocturne-notes-v1` from browser `localStorage`. Missing storage seeds one `Notes` folder and one `Welcome to Notes` note. Legacy fixed note IDs `note-1` through `note-4` and exact untouched `Untitled note` placeholders whose body is “Start typing…” are filtered out. The known former `folder-ideas`/`Ideas` folder is removed; notes tied to it are reassigned to the default folder. Other records, including edited notes titled `Untitled note`, are retained. If those recognized legacy placeholders were the only notes, the starter note is restored.
3. UI actions in `src/App.tsx` mutate React state: create/edit/delete notes, create/rename/delete folders, pin, search, and move. Title/body changes refresh the note timestamp. Search operates within the selected folder.
4. A React effect calls `saveAppState({ folders, notes })` whenever either array changes. This writes the full state JSON to localStorage.

This is a thin browser storage module, not yet a repository abstraction. CRUD operations are mostly implemented in the UI component, so a future persistence replacement requires introducing an interface and moving those operations behind it.

## Storage and Backend Boundary

Current persistence is local-only: no HTTP calls, user identity, authentication, server state, or synchronization are present. `loadAppState` and `saveAppState` in `src/data/store.ts` are the narrowest existing storage boundary. UI event handlers in `src/App.tsx` currently own actual mutations and should be refactored to call a repository/service before adding a remote backend.

### Future cloud-backend integration

No Supabase or Convex integration is implemented. A future agent should adapt the data boundary in `src/data/store.ts` into an asynchronous repository/service contract and route `App.tsx` operations through it. Expected operations include listing/creating/updating/deleting notes, listing/creating/renaming/deleting folders, searching notes, pinning, and moving notes. Backend records need the current note/folder fields plus ownership and server timestamps; file attachments should move to object storage or an equivalent file service instead of staying embedded as data URLs.

Decisions still open:

- Supabase versus Convex, and whether local-only mode remains supported.
- Authentication provider, account model, and whether anonymous/local notes can later be claimed by an account.
- Offline behavior, synchronization direction, conflict resolution, and deletion/tombstone policy.
- Whether folder and note IDs remain client-generated or become backend-generated.
- Attachment storage limits, upload lifecycle, and access control.
- Which search behavior is local, indexed, or server-side.

Keep these as design decisions; this repository currently provides no evidence for a selected cloud platform or sync policy.
